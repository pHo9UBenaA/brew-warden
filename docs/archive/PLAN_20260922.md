# Restore the original Homebrew wrapper design

Status: implementation in progress. Date: 2026-09-22.
Baseline: Codex task `01a0b958-0f2e-73e1-b35f-60b4822fedc2`,
the original security-tool design task, and its handoff commit `8105393`.
This is a migration record, not a second authoritative product specification.

## What was agreed

The final conversation, including the user's corrections, requires:

- A Go tool with a prefix interface: `bwd brew install ...` and `upgrade ...`.
  Checks pass -> execute without an extra approval; checks fail -> explain and stop.
- Prefer Homebrew's existing commands, options and verification. Supplement only
  demonstrated gaps, keeping Homebrew-specific behavior inside its adapter.
- Trust Homebrew itself. Do not defend against a compromised Homebrew runtime.
- Acquire release dates dynamically. Check requested packages and their complete
  required dependency closure before the first installation.
- Preserve the verified artifact/actual execution match. A successful preview or
  merely enabling attestation is insufficient. Unknown required evidence holds.
- Existing Homebrew plus BrewWarden should suffice; users should not assemble
  a separate verification toolchain. Existing gh is an allowed candidate.
- Keep mandatory hexagonal import boundaries and meaningful tests.

The original task explicitly left execution binding unresolved. It did not
require private APIs, a bundled Homebrew/Ruby copy, a custom gh executable,
Ruby recipe analysis, byte reconstruction of installed kegs, or a persistent
Ruby session. Nor did it promise that a subsequent unrestricted CLI invocation
would satisfy the binding requirement. Earlier replies in this task incorrectly
conflated these facts with either necessity or impossibility of private APIs.

## Why the implementation grew

Implementation selected a controlled native session to freeze inputs, retain
formula locks and block unexpected installer calls. Subsequent features were
built around that choice. Successful tests establish that this particular path
works; they do not establish that its complete machinery is the smallest viable
solution. The error was promoting a working experiment into the default product
architecture without completing and recording the simpler CLI comparison.

Keep the policy, providers, journal, CLI and import boundaries. Replace adapter
mechanisms incrementally rather than discard independently useful code or remove
security checks before their replacements work.

## Requirement versus mechanism

| Area | CLI-first replacement or investigation | Evidence needed before removing current mechanism |
| --- | --- | --- |
| Bottle downloads | `brew fetch --formula --bottle-tag=arm64_tahoe` and `brew --cache` | Exact selected tag, complete returned set, authenticated digest comparison, cached corruption and missing bottle rejection |
| Metadata | `brew info --json=v2 --formula` with controlled API/cache configuration | Authenticated metadata provenance, platform variations, exact closure and stale/offline behavior |
| Provenance | `brew verify --deps --json` and native attestation at install time | Every required subject accounted for, skipped checks rejected, credentials and helper installation controlled |
| Execution | Normal `brew install` / `brew upgrade` with frozen inputs | No re-resolution outside the approved closure, no source fallback, no unverified affected dependent, concurrent-change behavior |
| Release age and advisories | Retain Go providers unless equivalent native functionality is demonstrated | Source identity, publication time and advisory applicability remain explicit |
| Runtime packaging | Prefer the user's supported Homebrew installation | Version/capability detection, reproducible observations, compatible execution binding; a pin alone does not justify bundling another copy |
| State/history | Keep durable outcome recording; reduce native machinery | Interrupted operations remain distinguishable from success; do not infer success from current files |

## Known constraints, not impossibility claims

At inspected Homebrew revision `edb70f031e4170c780799633a1226ff73e1077f4`:

- `scripts/homebrew-probe.md` records a real preview re-resolution experiment.
  Separate dry-run calls consume changed recipes. This disproves treating a
  preview as an immutable execution plan; it does not disprove all CLI designs.
- `Library/Homebrew/lock_file.rb` uses nonblocking exclusive flock and closes
  descriptors on exec. An external process cannot simply retain those locks
  while expecting an ordinary child installer to acquire them. Releasing locks
  before launch loses continuous exclusion. This is a concrete constraint on
  that proposed design, not proof that no different design can work.
- `cmd/fetch.rb` can warn and skip an unavailable bottle. Check exit status AND
  the exact requested paths/digests. Its source fallback is not successful bottle
  acquisition. Never parse progress prose as verification evidence.
- Existing CLI install/upgrade experiments passed with frozen files, but their
  report explicitly did not prove concurrent external mutations. The later
  retained-lock experiment used private APIs. Do not cite it as CLI-only proof.

## Implementation sequence and acceptance

1. Replace the unnecessary private bottle-fetch calls with public CLI commands.
   Keep the existing authenticated-input, checksum and archive checks. Delete the
   replaced Ruby script rather than leave another selectable backend. Exercise
   the pinned real CLI in a host-write-denied sandbox and regression tests.
2. Run the remaining CLI comparisons above in isolated environments. Record
   each actual failure and the smallest necessary supplement. Do not expand
   compatibility code or claim a full CLI migration from a download-only test.
3. Replace metadata/provenance/execution boundaries only when their actual
   contracts are demonstrated. If continuous preflight/execute binding remains
   unavailable through public commands, state the exact unsupported guarantee;
   do not quietly weaken it or describe all current Ruby code as indispensable.
4. Remove obsolete native scripts, packagers and compatibility fixtures after
   their final callers disappear. Keep current docs synchronized with actual
   behavior, not planned behavior. A bundled runtime remains a removable choice.
5. Re-run isolated install, upgrade, existing-dependency, tampering, age-exception,
   interruption and CLI tests. Run `scripts/verify.sh`, appropriate broader
   checks, then Conventional Commits. Do not publish or modify host Homebrew.

## Results recorded in this change

- Removed `internal/adapters/homebrew/fetch.rb` and its embedded runtime entry.
  Product collection now uses `brew fetch` and `brew --cache` with fully qualified
  formula names and the exact platform tag. Go checks the complete result set,
  cache containment, authenticated hashes and archive layout before freezing the
  normalized download record. There is no alternate private fetch backend.
- `TestCLICacheResultsRequireEverySelectedBottle` rejects missing/extra results,
  a different formula/tag, cache escape and substituted bytes.
- `TestLiveNativeMetadata` passed against the pinned runtime with network and
  host writes denied. Real public CLI fetch consumed the cached jq/oniguruma
  closure and the subsequent candidate checks passed.
- In the same isolated test, `brew verify --json --bottle-tag=arm64_tahoe jq`
  failed for the intended `missing credentials` reason. The ordinary install
  command failed for the intended `already locked` reason while a parent held
  the formula lock; no keg was installed. Ruby is used only as test instrumentation
  for that lock experiment, not to change the CLI's locking behavior.
- `TestLiveCandidateCollection` passed through public network acquisition and
  all five evidence claims for both candidates. An initial run exposed the
  missing normalized `fetch.json` freeze record; that integration error was fixed
  before the successful run. Download-only success was not accepted as completion.

These results justify removing private fetching and retaining a supplemental
credential-free provenance path. They identify a real limitation of direct
CLI handoff under a retained lock. They do not prove that the complete current
runtime bundle, all other Ruby scripts, or any particular lock architecture is
indispensable. A full CLI-only execution replacement remains unverified.
